# Rendering: what crawlers actually see (REND)

Google renders JavaScript, but later and not always. Most AI crawlers (GPTBot, ClaudeBot, PerplexityBot) don't render it at all. Judge pages by the HTML the server sends.

### REND-01 · Content is in the server HTML, not only in JavaScript · blocker
- **Check:** crawler `client-rendered`, plus words per page in `seo-crawl.json`. Spot-check the H1, H2s, JSON-LD and an FAQ answer with the curl commands in `examples/snippets.md`.
- **Pass:** the H1, intro, main copy, FAQ, links and JSON-LD are all in the HTML response. Only interactive widgets need client JavaScript.
- **Fix:** use server rendering or static generation (see the framework file). Never disable SSR for components that contain text.
- **Crawler (outside checks):** `render-adds-text` (medium) flags a sample page whose rendered text has at least twice the words of its server HTML and at least 200 more (our own lines; a consent banner or a small widget adds less). Consent tools and chat widgets aren't counted, and pages already flagged `client-rendered` are left to that check.

### REND-02 · Collapsed content stays in the HTML · high
- **Check:** code: accordions, tabs, "show more", FAQ components that render with `{open && …}` or mount on click. Crawler `faq-not-visible` catches FAQ schema whose text is missing.
- **Pass:** collapsed content is rendered and hidden with CSS or a native `<details>` element.
- **Fix:** always render the content; toggle visibility with CSS, `hidden` or `inert`.

### REND-03 · Pages don't depend on a slow or failing API to render · high
- **Check:** code: page data fetching. Does a page call an external or scan API during render?
- **Pass:** page data comes from cached content (build time, ISR, or a cache). Live APIs are called only on user action. If they're down, the page still returns 200 with its content.
- **Fix:** move live calls behind the user action, and give the widget its own error state.

### REND-04 · Navigation uses real `<a href>` links · low
- **Check:** crawler `href-hash`. Code: `onClick` navigation, `href="#"`, `javascript:` links, links rendered only after JavaScript.
- **Fix:** use real links for navigation and `<button>` for actions.

### REND-06 · JavaScript doesn't fight the HTML · blocker
- **Check:** code: client code that edits robots meta, canonicals or status.
- **Pass:**
  - **Noindex:** a noindex in the server HTML can stop rendering, so removing it with JavaScript may never take effect.
  - **Canonical:** set it in the server HTML; JavaScript must not change it.
  - **Status:** only 200 pages are reliably rendered. SPA "not found" views redirect to a URL the server answers with 404, or inject noindex.
  - **Routing:** use the History API, not `#` routes.
- **Crawler:** with outside checks on and Chrome or Edge installed, up to 10 sample pages are rendered headless and compared with the raw HTML: title, canonical, robots, meta description, H1, JSON-LD count and link count (`render-changes-head`, high, when JavaScript changes, adds or removes the title, canonical or robots tag; `render-changes-text`, low, when it changes, adds or removes the meta description, or changes or removes an H1 the raw HTML had: Google reads what JavaScript sets, as its JavaScript SEO basics page, updated 4 Mar 2026, says, but crawlers that don't run JavaScript see the server's version; `render-adds-content` under REND-01 when the H1, JSON-LD or many links appear only after rendering). Pages with a meta refresh are skipped. With `--render all` on top of `--outside`, every indexable page is rendered instead of the sample, up to 200 (about 5 s a page); the time estimate prints before the first render, and a note says how many pages the cap left out. When Chrome can't load a page (it reports `net::ERR_…`, shows its own `chrome-error://` page or returns an empty page), that page isn't compared: the failure goes into the notes, and REND-06 stays under Limits when no page rendered.
- **Login and paywall screens:** a render that shows a login screen (a password field, with "log in" or "sign in" in the title or H1) or a paywall (Google's paywalled-content markup, `isAccessibleForFree: false`, or a paywall layer such as Piano's `tp-modal`) isn't compared or measured as the page. It's reported in the notes and the report. Nothing is ever typed into a form.
- **Paid text sent to everyone:** crawler `paywall-text-sent` (low, a possible issue, no browser needed): an indexable page whose JSON-LD says `isAccessibleForFree: false` and names its paid sections with `hasPart` → `cssSelector` (Google takes `.class` selectors only), while the HTML the crawler got without logging in holds 150 or more words in those sections (our own cut-off). Google's JavaScript troubleshooting page (paywall item added 28 Aug 2025): sending the full content and hiding it with JavaScript "isn't a reliable way to limit access to the content"; send it only "once the subscription status is confirmed". Its updates log adds that the pattern "makes it difficult for Google to automatically determine which content is paywalled". Fine on purpose for a metered site's free articles. Apple's Applebot (support.apple.com/en-us/119829, 4 Sep 2026) doesn't use pages marked `isAccessibleForFree: false` as context for AI answers in Apple products; it reads the page-level property only, not `hasPart`. Microdata paywall markup isn't read.
- **One chosen page:** `--render-page <url>`, with `--outside`, renders a page the owner picks at phone size, after optional `--render-steps "scroll; click .load-more; wait 1000"` (scroll through the page, click a CSS selector, wait up to 10 s; 20 steps at most). The report shows its word count before and after, what changed from the raw HTML, browser errors and any login or paywall screen; screenshots are `chosen-mobile.png` and `chosen-mobile-full.jpg`. Information only.

### REND-07 · Mobile shows the same content as desktop · blocker
- **Check:** compare a mobile and a desktop render of key templates (Google indexes mobile-first, fully since 2024).
- **Pass:** same main content, headings, structured data, titles, descriptions, alt text and robots meta on mobile. Primary content isn't hidden behind interaction-only lazy loading.
- **Crawler:** with outside checks on and Chrome or Edge installed, the render sample is also loaded at desktop (1366×768) and phone size (390×844, touch, mobile user agent), with screenshots in `seo-audit/screenshots/`. `mobile-content-missing` flags a page whose main text on a phone has under 70% of desktop's words, counted from the page's DOM (so sections collapsed with CSS or a closed `<details>` still count), or whose phone H1 shows less than half of the desktop H1's words. Without outside checks REND-07 stays under Limits.
- **More screenshots (outside checks):** each sample page also gets a whole-page shot at desktop and phone size (`-desktop-full.jpg`, `-mobile-full.jpg`, scrolled through first so lazy images load, up to 12,000 px tall), and first screens at 1920×1080 (`-desktop-1920.png`) and tablet size, 768×1024 (`-tablet.png`). The last two resize the desktop load instead of loading again, so a page that lays itself out only on load keeps its desktop layout there. With `--clean-screenshots`, `-desktop-clean.png` and `-mobile-clean.png` hide cookie bars and chat widgets (made only when there was one to hide).
- **Look at the screenshots:** open them and check for text that overlaps or is cut off, images that are stretched, squashed or blurry, and layouts that break at one size. Report each defect with its file name; the crawl's notes repeat this.

### REND-08 · HTML stays under Googlebot's 2 MB limit · high
- **Check:** crawler `html-size` (flags anything over 500 KB; over 2 MB is high).
- **Pass:** Googlebot reads only the first 2 MB of each HTML response; content past that isn't indexed. A PDF gets more: Googlebot reads its first 64 MB (Google's Googlebot docs). Keep the title, meta, canonical and JSON-LD early in `<head>`, and move huge inline JSON (hydration data, big lists) out of the document.
- **Head tags after `</head>`:** crawler `head-tags-late` (low) when the title, meta description, canonical or robots (or googlebot) tag comes after `</head>` (or after `<body>` when there's no `</head>`); SVG titles, scripts and comments don't count. Google's "Inside Googlebot" post (31 Mar 2026) asks for meta tags, `<title>`, `<link>` elements and canonicals "higher up in the HTML document", and Google accepts a canonical only in the `<head>`. Google does respect a robots tag in the body (robots meta tag docs), and the crawler reads body tags as a fallback for every other check. Next.js 15.2+ streams metadata into the body when `generateMetadata` is slow: browsers and Googlebot get it there, the bots matching Next.js's `htmlLimitedBots` list (Bingbot, Applebot, Twitterbot, Slackbot, facebookexternalhit and others) get it in the head. The crawler's user agent, `seo-supervisor-crawler`, isn't on that list, so it sees the browser version. `htmlLimitedBots: /.*/` in next.config turns streaming off.

### REND-05 · One title, canonical, robots tag and schema graph per page · high
- **Check:** crawler `title-multiple`, `canonical-multiple`. Code: layouts that hard-code a title, or two SEO plugins or helpers both writing tags.
- **Fix:** emit head tags from one place.

### REND-09 · Pages declare a doctype, a charset and a mobile viewport · medium
- **Check:** the crawler: `<!doctype html>` first, a charset (meta tag or Content-Type header) and `<meta name="viewport" content="width=device-width, …">`.
- **Pass:** every page has all three, from the shared layout.
- **Fix:** add them to the root layout. Without a doctype browsers use quirks mode; without a viewport phones show a zoomed-out desktop page, and Google indexes the mobile version.
- **Charset mismatch:** `charset-mismatch` (medium) flags a page whose Content-Type header and meta charset name different encodings. Names are compared as browsers read them, so `latin1`, `iso-8859-1` and `windows-1252` agree. The header wins, so text saved in the meta tag's encoding comes out garbled; serve and declare UTF-8 in both.
- **Crawler (outside checks):** on the phone load, `mobile-overflow` flags a page wider than the screen (sideways scrolling; overflow clipped with `overflow-x: hidden` or `clip` on html or body isn't flagged) and `mobile-small-text` flags main text (the size most `p`, `li` and `td` text uses) under 12 px. Pages without a mobile viewport are left to `doc-basics`.
- **Tap targets (outside checks):** `tap-targets-small` (low) flags a phone page with links or buttons under 24×24 CSS px whose 24 px circle, centred on each, touches another link or button or another small one's circle (WCAG 2.2 success criterion 2.5.8, Target Size (Minimum), with its spacing exception; Lighthouse 12 replaced its tap-targets audit with this standard's `target-size`). Links inside a sentence, visually hidden skip links and closed off-screen menus don't count. Fix with padding, or 24 px from the centre of one small icon to the next.
- **Form fields (outside checks):** `input-zoom` (low) flags a phone page with visible text fields, selects or text areas whose text is under 16 px, because Safari on iPhone zooms the page in when one is tapped. WebKit's `-[WKWebView _zoomToFocusRect:…]` (`Source/WebKit/UIProcess/API/ios/WKWebViewIOS.mm`) zooms to 16 ÷ the field's text size, capped at the viewport's `maximum-scale`, and skips a change under 10%, so a 15 px field doesn't zoom; `user-scalable=no` stops it too (`_zoomToRevealFocusedElement` in `WKContentViewInteraction.mm`). Sizes are measured in Chrome, which gives unstyled fields 13.33 px, so those count. Hidden, disabled and read-only fields, checkboxes and buttons don't, nor fields off the screen sideways, out of the tab order (`tabindex="-1"`) or inside `aria-hidden="true"`, as a sign-up form's spam trap is (Mailchimp's is all three). Fix with `font-size: 16px` (or `1rem`) on fields, not with `maximum-scale=1`, which on Android also stops visitors zooming in to read.
- **Phone text (outside checks, information only):** main text from 12 px up to 16 px on the phone load goes in the notes. It never becomes a finding or changes the score; under 12 px stays `mobile-small-text`.

### REND-10 · No obsolete HTML tags · low
- **Check:** crawler `obsolete-tags`: `<frameset>`, `<frame>`, `<marquee>`, `<blink>`, `<font>` or `<center>` anywhere in the server HTML. It also flags `<acronym>`, `<applet>`, `<basefont>`, `<bgsound>`, `<big>`, `<dir>`, `<isindex>`, `<nobr>`, `<spacer>`, `<strike>` and `<tt>` (WHATWG HTML, Obsolete features). `<iframe>` is fine, and so are custom elements such as `<font-awesome-icon>`.
- **Pass:** content lives in ordinary pages, not frames, and styling lives in CSS.
- **Fix:** replace a frameset with real pages, each with its own URL and links (search engines index each frame's document on its own, without the frame around it). Move what `<font>`, `<center>`, `<marquee>` and `<blink>` do into CSS. Old templates and text pasted from word processors are the usual source.

### REND-11 · Phones get a working menu, and pages that aren't crowded with ads · medium
- **Check (outside checks):** each sample page is loaded once more at phone size.
- **Menu:** `mobile-menu-closed` (low) flags a page that hides on phones at least 3 menu links desktop shows (no visible copy anywhere on the page), where Chrome tapped the menu button (found by its name: menu, navigation, hamburger, nav-toggle) and under half of those links appeared (3 and half are our own lines). Cookie bars and chat widgets are hidden first so they can't take the tap. No button found, or one covered by another layer, goes in the notes and the report instead.
- **Ads:** `mobile-ad-density` (medium) flags a page where ads take more than 30% of the height between the header and the footer on a phone, overlaps counted once. That is the Better Ads Standard's "mobile ad density higher than 30%" (betterads.org/mobile-ad-density-higher-than-30: ads' heights in the main content over its height, headers and footers left out). Google's page-experience questions ask whether content avoids "an excessive amount of ads that distract from or interfere with the main content". Ads are found by AdSense, Google Ad Manager, Amazon and Xandr markup and common ad-slot classes. An ad network that serves nothing to a fresh headless browser can't be measured, so a pass here means no heavy ad layout was seen.
- **Fix:** give the menu button a working click handler (or a `<details>` element) that shows the menu above other layers. Show fewer ad slots on phones.

### Render sample · information only
With outside checks on, `renderSample` in `seo-crawl.json` holds what the second load of each sample page saw. None of it changes the score.
- **Browser errors:** uncaught script errors, `console.error` calls and failed loads the browser logs, up to 10 a page. The browser's own `/favicon.ico` request and requests the audit itself blocked are left out.
- **First screen:** whether the H1 and a button (a call to action outside the menu and footer) are on the first screen at desktop and phone size. Our own measures: Google's guidance doesn't name the "first screen".
- **Hidden text:** words hidden by the `hidden` attribute, `display:none`, `aria-hidden` or a screen-reader class, leaving out accordions, tabs, menus, dialogs, sliders and closed `<details>`. Google's spam policies don't count those or text meant for screen readers as hidden text; its examples of abuse are white-on-white text, text behind an image, text placed off-screen with CSS, and text with font size or opacity 0. The report lists pages with 50 or more hidden words (our own line); check that the text isn't keyword stuffing.
- **Jump links:** links to a `#fragment` on the same page whose target isn't there, and a load at a heading's `#id` lower on the page: did the page stay there and keep the `#id` in the address? Google's "Read more" deep links need both: its snippet guidance says to avoid JavaScript that controls the scroll position on load and, with History API calls or `location.hash` changes on load, not to remove the hash fragment.
