# Report format

The audit is one JSON file, `seo-audit/seo-audit.json`. The same file carries the fix history, so a later fix run updates it instead of starting over. `scripts/render-report.mjs` turns it into two files, and a third on request:
- **`seo-audit/seo-audit.html`:** a self-contained page (offline, light and dark, phone, print). The Overview leads with action, in this order: the verdict and score (with what fixing the blockers unlocks), **Fix first** (up to 5 code fixes, each with its `/seo-fix F-…` line), **Needs you** (up to 3 of the owner's tasks and decisions; all of them are on the Decisions tab; a finding the audit lists a decision for is the owner's, a won't-fix finding is in neither list, and nothing is in both), what's moving the score, a one-line scope linking to Limits (when the crawler noted that over half the pages are noindex, it says so, with the `--ignore-noindex` hint), and the key numbers (pages checked, open issues, fixed this run, clicks from Google when connected, Core Web Vitals when there's field data). The tabs follow in this order: Plan (setup mode, with a `plan`; first, before the Overview, while the plan is proposed), Findings, Decisions, Search & AI, Speed, Links, Site & content, Since last audit (with a `diff` or a `changeCheck`), Changes, Passed and Limits. The Markdown keeps the same order. The information panels sit on the four topic tabs, each shown only when it has data:
  - **Search & AI:** search traffic, search ideas, and AI crawlers, agents and answers;
  - **Speed:** speed, and Lighthouse when it ran (the card is "Speed and Lighthouse" then, else "Speed");
  - **Links:** internal links, links from other sites, and this site's links to other sites;
  - **Site & content:** score views (estimates, not part of the score), structured data, local business with the rank grid, content and writing, and site hygiene.

  The Findings, Decisions, Changes, Passed and Limits tabs hold the detail, with up to 10 evidence rows per finding. Every open finding except a won't-fix one ends with its next step: "Next step: `/seo-fix F-012` fixes it and checks the fix.", or for the owner's part, "`/seo-fix F-001` asks you first". The audit timeline and the change check are on Since last audit, the check settings are on Limits, and Limits lists under "Not shown" any result that was produced but couldn't be shown, with why. In the Markdown, each topic is a `##` section and each panel a `###`, in the same order, with the findings near the top. Only "How the score works", a folded box in the page's score panel, comes last in the Markdown.
- **`seo-audit/seo-audit.md`:** the full report as Markdown, with every evidence row. Use it for reading in an editor, diffing between runs, and pasting into tickets. Text from the audit file is escaped in the Markdown; `code` spans and **bold** in the agent's own text stay, as on the page.
- **`seo-audit/seo-audit.pdf`,** only with `--pdf`: the HTML report printed by the installed Chrome or Edge, every tab in turn with every collapsed panel opened, for a client or a manager. Without a browser it says so and writes the other two.

The renderer ends with a short receipt: the score and band, what fixing the blockers unlocks, the open counts and the files written. Repeat it in chat.

**Links:** only a full `http://` or `https://` address becomes a link (evidence `url`, `site.url`, `attribution.url`, `googleUpdates` links, a plan `draft`, which may also be a plain path next to the report); anything else is shown as text. The page has a Content-Security-Policy that runs only its own scripts.

**Several sites:** `node scripts/dashboard.mjs <folder> <folder> … [--out dashboard.html]` (or `npx seo-supervisor dashboard`) reads each folder's `seo-audit.json` and prints one line per site, lowest score first, with the same score model. `--out` also writes one offline HTML page linking to each report. It reads local files only.

## The score (computed by the renderer, never by hand)

- Every checked rule is worth 10 points: each rule in `passed`, plus each distinct `rule` among `findings`. A finding without a rule counts as its own rule.
- A rule earns 10 if it passes or all its findings are `fixed`. Otherwise it earns by its worst open finding: low 8, medium 6, needs-decision 6, high 3, blocker 0. `wont-fix` counts as open. While any open finding isn't `wont-fix`, the score stops at 99, so 100 means nothing is left to fix; the same holds for area and page scores.
- **Score** = points earned ÷ points possible × 100, rounded, and at most 99 while a finding that isn't `wont-fix` is open.
- **Blocker cap:** each open blocker caps the score. One caps it at 59, two at 49, three at 39, and so on, never below 9. The report says when the cap applies, and shows the score the site reaches once the open blockers are fixed: the same model, with those blockers treated as fixed. After a fix run it shows the change: the total's, or the checked-rules score's when the cap holds the total still.
- **Area scores** use the same rules within each `category`.
- **It's our score, not Google's.** "How this score works" says so: it counts only the rules the audit checked, and search engines don't use it. Never call it a Google score or a ranking.
- **Page scores:** each page with open findings gets its own score, shown collapsed on the Site & content tab (the 10 lowest) and in full in the Markdown. It's the same model over the site's checked rules, counting only the open findings whose `evidence` names that page. Pages come from evidence URLs on the site's own host (`www.` or not); a broken link, a link to a redirect and a link to a missing #part name the page that holds the link, with the target in the detail, so they count against that page; other sites' pages and files such as `sitemap.xml` and `robots.txt` are left out. It's labelled "SEO Supervisor's own score, not Google's" and never changes the site or area scores. Since evidence holds examples, a finding with a bigger `count` can touch pages not listed.
- **Score views:** with `trustSignals`, the Site & content tab adds a "Score views" panel, labelled "Estimates, not part of the score". **Trust signals (E-E-A-T)** is signals found ÷ signals that apply × 100, rounded (8 of 11 is 73), labelled "SEO Supervisor's own check, not a Google score". Missing signals are suggestions listed with what to add: they aren't findings and never change the overall or area scores. **Local SEO** and **Content quality** are the "Local business" and "Headings & content" area scores under those names, each shown only when its area has checked rules.
- **Bands:**

| Score | Band |
| --- | --- |
| 90–100 | Excellent |
| 75–89 | Good |
| 60–74 | Fair |
| 40–59 | Poor |
| 0–39 | Critical |

Consequences for the JSON:
- Give every finding a `rule` and a `category`; they drive the area scores.
- Record passed rules with their `category`.
- Don't list a rule as both passed and failing.
- Rules under `notChecked` don't count either way.

## Build it in this order

1. Start from `seo-audit/seo-crawl.json` and, if you ran it, `seo-audit/content-scan.json`. Copy their `findings`, `passed`, `notChecked` and `notes`. Their findings already carry `what`, `why` and `fix`; rewrite `what` in plainer words when you can say more than the example.
2. Review each finding against the SEO profile. Keep it, change its severity, or drop it and say why in `notes`. **Merge** findings that share a root cause into one: e.g. near-duplicate pages (crawler), templated intros (content scan) and reused FAQs all come from one template, so they become one finding listing every symptom in `what`. Then look **across areas** for the patterns below. When the same pages show both signs, write one finding about the cause: name its rule as the field rules say, list the other rules as "Related:" in `what`, and take the highest severity.

   | Same pages show | Usually means | The one finding |
   | --- | --- | --- |
   | Thin pages (CONTENT-05) and two pages for one query (INTENT-02) | Several weak pages split one topic | Merge them into one hub page and 301 the rest to it (URL-07). Merging and removing pages is the owner's call: `fixBy: "owner"`. |
   | Templated text (CONTENT-04) and duplicate titles or descriptions (META-01, META-02) | One template fills them all | Fix the template, with each page's own facts. |
   | Orphan pages (LINK-02) also missing from the sitemap (MAP-03) | Pages the site has forgotten | Link them from their hub and list them, or let the owner retire them. |
   | Sitemap URLs that redirect or fail (CRAWL-06) and canonicals that disagree (URL-04) | Sitemap and canonical are built from different URL sources | Build both from the one URL helper. |
   | Content, links or H1 only after JavaScript (REND-01 render-adds-content or render-adds-text) and missing H1 or schema in the crawl (CONTENT-01, SCHEMA-03) | The page is built in the browser | One REND-01 finding listing what's missing from the server HTML. A page the crawler already reports client-rendered comes with just that one REND-01 finding, so there's nothing to merge. |
   | Slow LCP (PERF-01) and heavy images (PERF-08) | The hero image | One PERF-01 finding naming the image and its fix. |
   | noindex (CRAWL-02) on pages the sitemap lists (MAP-02) | The two signals disagree | One finding with a decision: which is meant? |

   These are our own rules of thumb, not Google's. Merge only when the evidence shows the same pages; two problems that only sit in the same area stay two findings.
3. Add the findings from the code and content inspection, with `file` and `line` evidence.
4. Add `decisions` for questions only the owner can answer.
5. Add `notChecked` for anything you couldn't verify or that doesn't apply, with the reason (e.g. "Core Web Vitals field data: site not live yet", "SHOP rules: not an e-commerce site").
6. Write `summary`: two or three plain sentences. **The first sentence is the verdict**; the report shows it at the top and you repeat it in chat.

## Shape (illustrative values)

```json
{
  "site": {
    "name": "Example Plumbing Co",
    "url": "https://www.example-plumbing.com",
    "framework": "Next.js 16 (App Router)",
    "siteTypes": ["local-business", "services"],
    "profile": "docs/seo-profile.md"
  },
  "run": { "mode": "audit", "date": "2026-11-17", "pagesCrawled": 120, "auditor": "seo-supervisor" },
  "summary": "The build is solid, but the 80 city pages are templated and would launch together. Fix the two blockers first, then the soft 404.",
  "findings": [
    {
      "id": "F-001",
      "rule": "LOCAL-02",
      "severity": "blocker",
      "category": "Local business",
      "status": "open",
      "title": "80 city pages differ only by the town name",
      "what": "Intros and FAQs are the same template with {city} swapped; the crawler found 1,204 page pairs sharing over 60% of their main text. Related: CONTENT-04.",
      "why": "Google treats pages that only swap a place name as doorway pages and can filter them or hold down the whole site.",
      "evidence": [
        { "url": "https://www.example-plumbing.com/drain-cleaning-springfield/", "detail": "74% shared with /drain-cleaning-shelbyville/" },
        { "file": "src/lib/content.ts", "line": 214, "detail": "intro template only swaps {city}" }
      ],
      "count": 1204,
      "fix": "Publish only cities with real local proof (jobs, photos, reviews from that town), each with its own intro and FAQs, in `src/data/cities.ts`. Hold the rest with the publish flag."
    }
  ],
  "decisions": [
    {
      "question": "Is commercial drain work actually offered?",
      "context": "The content data marks it unconfirmed, but 20 city pages exist for it.",
      "options": ["Yes, keep the pages", "No, remove them and 301 to /services/"],
      "recommendation": "Keep them unpublished until the owner confirms."
    }
  ],
  "passed": [
    { "rule": "URL-04", "title": "Every indexable page has a self-referencing, absolute canonical", "category": "URLs & canonicals", "detail": "src/lib/seo.ts:41 builds it from SITE_URL + path" }
  ],
  "notChecked": [{ "area": "Core Web Vitals field data", "reason": "No CrUX data for a site that isn't live yet." }],
  "notes": ["Crawled a production build on localhost:3123 with --ignore-noindex (pre-launch)."]
}
```

`date` is `YYYY-MM-DD`, shown as that day on every machine; a full date and time is shown by its UTC day.

## Field rules

| Field | Rule |
| --- | --- |
| `id` | `F-001`, `F-002` and so on. **Never renumber** on later runs; fix history depends on stable IDs. New findings get the next free number. |
| `rule` | The rule ID from `rules/` or `site-types/`. When several rules cover the problem, use the **most specific** one (a site-type rule beats a general rule), name the others in `what` ("Related: CONTENT-04"), and take the **highest** severity among them. |
| `severity` | `blocker`, `high`, `medium`, `low` or `needs-decision`. Definitions are in SKILL.md. |
| `status` | `open`, `needs-decision`, `in-progress`, `fixed` or `wont-fix`. `fixed` requires a re-check. |
| `title` | States the problem, with a count if it applies: "12 titles are longer than 60 characters". Not "Title issues". |
| `what` | What is wrong, in plain words, with numbers. Written for the site owner, not for an SEO expert. The scripts write it as "Found on `url` (detail)." or "N cases, for example `url` (detail).", with web addresses in code spans. |
| `why` | The consequence: lost rankings, missed indexing, a penalty risk, wasted crawl budget. |
| `evidence` | Up to 100 items. Each has a `url`, or a `file` plus `line`, and a short `detail`. Group repeated issues into one finding and set `count` to the full total. Use public URLs (the crawler's local URLs mapped to the production origin) unless production is still a different, old site; then keep the local URLs and say so in `notes`. |
| `fix` | The concrete change and *where* to make it: the shared helper or file, not "every page". |
| `fixBy` | Optional. Set it to `"owner"` when only the owner can resolve the finding: content or facts, CMS edits, business decisions, removing pages. The report labels it **Needs you**, and fix mode leaves it alone without the owner's go-ahead. Leave it out when the agent can fix the finding. |
| `effort` | Optional. Roughly how long the fix takes: `"quick"` (under 30 minutes), `"hours"` (an hour or two) or `"half-day"` (half a day or more). Set it when you write the finding. The report shows it on the finding card ("Effort: an hour or two"); any other value shows nothing. |
| `check` | The crawler's (or another script's) check id, e.g. `"no-hsts"`. Keep it when you copy a finding from `seo-crawl.json`: check settings and re-check commands use it. Findings you write yourself have none. A check that's renamed keeps working: `ID_ALIASES` in `scripts/crawl/catalog.mjs` maps each old id to its new one, and settings.json, the report, the dashboard and `issues.mjs` read old ids through it. When you carry a finding's status (`wont-fix`, `fixed`) or ID over from the last audit, match an old `check` to its new id there. |
| `decision` | Optional, for findings that need an owner's call: `{ "question", "options": [], "recommendation" }`. |
| `fixed` | Fix mode only: `{ "summary": "what changed. Watch: titles over 60 characters on the next crawl, down to 0, right after the deploy.", "files": ["src/lib/seo.ts"], "verified": "re-crawl 17 Nov: 0 titles over 60" }`. |
| `passed[].detail` | Optional evidence for a pass, e.g. the `file:line` that implements it. |

## Check settings

`seo-audit/settings.json` (beside the audit file) may hold `"checks": { "off": ["check-id"], "severity": { "check-id": "medium" } }`. The renderer, the dashboard and `issues.mjs` apply it to every finding with that `check` before anything else: a check that's off is left out of the findings and the score (as if it hadn't run), and a severity counts at its new value. A finding that's a blocker stays as it is. The report lists every setting in a collapsed "Check settings" panel on the Limits tab (a section in the Markdown) with how many findings each changed, and the receipt repeats it. Unknown check ids, severities that aren't `blocker`, `high`, `needs-decision`, `medium` or `low`, a wrong shape and a file that isn't JSON each give a plain warning there. A setting that names a check's old id still applies, with a warning asking to rename it.

**Re-check commands.** Findings whose `check` a one-line command can prove (headers and HSTS, redirects, robots.txt, canonicals, noindex) show "Check the fix yourself" with a `curl` command built from the first evidence URL, on the card and in the Markdown. A URL that isn't plain http(s) ASCII, or has a quote, `` ` ``, `$`, `\` or `{}[]`, gets no command. One note on the Findings tab says how to run them (on Windows, `curl.exe` in PowerShell).

| `aiBots`, `landmarks` | The crawler. `aiBots`: `[{ bot, vendor, kind, robots, mayIgnore? }]`, each AI crawler; `robots` is `allowed`, `blocked` (its own group, or a second name the vendor accepts, such as `YandexAdditional`), `blocked-by-googlebot` (Applebot follows the Googlebot group when it isn't named) or `blocked-by-star` (by `User-agent: *`; never for `YandexAdditionalBot`, which reads only a group that names it). `trainingOptOut`: `not-set`, `blocked`, `partly` or `allowed`, the shared `User-agent: __usage_ai-training` group (an IETF draft; `*` doesn't cover it), shown as one line in the same panel. `contentUsage`: `[{ agents, rule }]`, aipref `Content-Usage` lines as written (`agents` is the group's user agents, or null for a line above the first `User-agent:` line), the first 20. `botPreferenceSync`: `true` when robots.txt carries a Cloudflare block, `# BEGIN Cloudflare Managed content` or `# BEGIN Cloudflare Bot Preference Sync`, in any case. `aiBotPaid`: `[{ url, bot, price? }]`, pages that answered the `--ai-bot-probe` crawler with 402 Payment Required, `price` from the `crawler-price` header. `landmarks`: `{ checked, count, pages: [{ url, missing[] }] }`, pages without a main, nav, header or footer landmark, the first 20 (AI-05) | A collapsed "AI crawlers and agents" panel on the Overview (a section in the Markdown): a table of the crawlers, Brave's Googlebot fallback (with the table), the Bot Preference Sync note, the Content-Usage lines and the pages that asked to be paid, the landmark line and its pages, and Lighthouse's Agentic browsing checks (`lighthouse[].agentic`), escaped. Information only. |
| `appLinks` | The crawler, when a page promotes an app (a Google Play or App Store link, `apple-itunes-app`, an `android-app://` alternate): `[{ platform, file, page, missing, problem }]`, each app link file (`/.well-known/assetlinks.json`, `/.well-known/apple-app-site-association`) that's missing (`missing: true`) or broken (bad JSON, wrong shape, a redirect, Android's content type, an error) | A collapsed "App links and PDFs" panel on the Overview (a section in the Markdown), escaped: a missing file is fine if the app doesn't open the site's links. Information only. |
| `pdfLinks` | The crawler: `{ count, pdfs: [{ url, pages, menu }] }`, PDFs on the crawled site that 3 or more indexable pages (our own cut-off) or a `<nav>` link to, the first 20 | The same panel: each PDF's path and how many pages link to it, with Microsoft Advertising's advice (8 Oct 2025) to keep core information in HTML. Information only. |
| `bots.<name>.ipCheck` | `log-scan.mjs --verify-ips`, in `log-scan.json` only: `{ verified, other, unknown }`, that bot's requests from the vendor's published addresses (for YandexBot, addresses whose reverse DNS name is on yandex.ru, yandex.net or yandex.com and leads back to them; not checked with a saved-lists folder), from other addresses, and from lines with no address or a DNS lookup that got no answer | In the "Server logs" panel's bot table: "9,200 (9,150 from Google's addresses)". Quote it in chat beside the bot counts too: requests from other addresses are likely fakes. |

**Result files the report reads.** You don't have to copy information-only data: for whatever the audit JSON lacks, the renderer reads the result files beside it in `seo-audit/`: `seo-crawl.json`, `seo-diff.json` (`diff`), `google.json`, `keys.json`, `log-scan.json` (`logScan`), `keyword-ideas.json` (`keywordIdeas`, `linkIdeas`, `queryGaps`), `geo-grid.json` (`geoGrid`), `ai-answers.json` (`aiAnswers`) and `change-check.json` (`changeCheck`). It writes nothing back. The rules:
- **The audit wins.** The fields one panel reads come from the audit JSON when it has any of them, else from the file, never some of each. A panel's companions, such as the pages beside the searches and the period, come from that same source.
- **Same site only.** A file that names a site (its `site` or `siteOrigin`, or the addresses in `log-scan.json`'s findings) is used only when that's the audit's `site.url`, `www.` or not. A local address, or a file that names none, can't be compared and is used.
- **Dated.** A panel filled from a file says so: "From your server logs (log-scan.json, 12 Nov 2026)." The date is the one the file records (`crawledAt`, `when` or `date`). A file with none is dated by when it was saved, and the line says so: "(google.json, file saved 12 Nov 2026)".
- **Out of date.** A file more than 30 days older than the audit's `run.date` (our own line) is skipped.
- **Nothing vanishes silently.** A file skipped for another site or its age, or one that can't be read, gets a line under "Not shown" on the Limits tab. A missing file stays quiet: that tool wasn't run, and the scope line and Limits already say what wasn't checked.
- **Never the score.** Findings, `passed`, `notChecked` and `notes` are never read from these files, so they can't change the score. Merge those by hand as before.

Rendering a raw `seo-crawl.json` or `content-scan.json` reads no other file.

Findings from `gsc-import.mjs` (INTENT-02…04) and the intent checks (INTENT-01, INTENT-05) are ordinary findings in the "Search intent" area. Findings from `google.mjs fetch` are ordinary findings too: key pages Google hasn't indexed (CRAWL-02), a different Google-chosen canonical (URL-04), sitemap errors (MAP-01) and rich-result errors Google reports for inspected pages (SCHEMA-08, `gsc-rich-result-errors`). Skipped or failed connections go under Limits with the reason and never change the score.

## Since last audit

`seo-diff.mjs --history seo-audit/history seo-audit/seo-crawl.json --out seo-audit/seo-diff.json` compares the crawl with the newest one filed in `seo-audit/history/`, adds `timeline`, and files the crawl there as `<date>-seo-crawl.json` (with the time too when another crawl has that day; never over another crawl). The first crawl is only filed, and no diff is written. Two files given by hand still work as before. `--fail-on-regressions` exits 1 after writing, for scheduled runs (`examples/scheduled-runs.md`).

More of `diff`, each compared only when both crawls recorded the field (`compared` then holds `h2`, `hreflang` or `sections`):

| Kind | Where | What |
| --- | --- | --- |
| `h1-changed` | Other changes | The H1's text (`h1Text`) is different. A removed H1 stays `h1-removed`. |
| `h2-changed` | Other changes | H2s came or went, or their count changed: "H2s changed: 3 → 4; − Prices · + Plans and prices". A new order alone isn't a change. |
| `hreflang-changed` | Regression when alternates only went, improvement when they only came, else other changes | Each language and its target, with targets on the site's own hosts read as paths, so a local crawl matches the live one: "hreflang changed: − de → /de/b/". |
| `schema-retired-removed` | Other changes | A type whose rich result Google retired (`retired` in `google-rich-results.json`, except the ones marked `keep`) was taken off. Not a regression; removing FAQPage still is. A retired type's fields aren't compared. |
| `section-shrunk` | Regression | A top-level section (the crawl's `sections`) lost half its pages and at least 10 (our own line): "Section shrank: 40 → 12". Never sent to IndexNow or Bing. |

- **Open Graph:** `og-removed` and `og-added` also count `og:description` and `og:url` once both crawls keep them.
- **Length:** `content-shrunk` and `content-grew` now need at least 50 words and a third fewer, or half as many again (our own lines).
- **Partial crawls:** a crawl that stopped at `--max`, or covered one part of the site (`section`, from `--include`/`--exclude`) that the other crawl didn't, missed pages. When it's the new crawl, `removed` is empty and `removedUnknown` is `true` (`--max`) or `"section"`; when it's the last one, `added` is empty and `addedUnknown` says why. Since last audit says why in a plain sentence. Internal links and sections are compared only when both crawls were whole.
- **`timeline`:** `[{ date, pages, findings, regressions, improvements, added, removed }]`, one row per filed crawl, oldest first. Each row after the first counts its changes from the row before; `null` means it couldn't be told. From 3 rows on, a collapsed "Audit timeline" table on the Since last audit tab (a section in the Markdown), newest first, 100 rows at most. Information only.
- **`addedBurst`:** `{ pages, before, share, sections: [{ path, pages }], examples: [{ path, title }] }`, only when at least 50 pages are new and that's at least 20% of the pages that loaded in the last crawl (our own line). `sections` counts the new pages by top-level folder, using the crawler's `sections` rule (largest first, 20 at most). `examples` holds 10 new pages, taken from each folder in turn, so a new folder stands out. It shows as "Many new pages" at the top of Since last audit (and of its Markdown section): "212 new pages appeared since the last audit (on 1 Oct 2026), 35% more than the 600 pages it found. If you didn't add them, check for hacked or spam pages", with a link to Google's help on hacked content (Search Console Help, "Hacked: URL injection"), the count per folder, and the examples with their titles, escaped. Information only: it isn't a finding or a regression, it doesn't change the score, and it never judges what the pages are about. It's absent on a first audit, for normal growth, and when the last crawl didn't reach every page (`addedUnknown`).
- **`googleUpdates.posts`:** `google-updates.mjs --blog` adds `[{ title, date, url }]`, the Google Search Central blog's posts in the period (launches and policy changes; Search Central Live events left out). One quiet line on the Search & AI tab and in Since last audit: "Google Search Central announcements in this period: Update to the Site Reputation Policy (28 Aug) · …", titles escaped and linked. Dates only, never a cause.

## Audiences (the audience check)

Written by you, not a script, as `audience.md` says. Leave it out when the owner named no audiences.

```json
"audiences": [
  { "name": "Landlords", "wants": "a fixed price for a gas safety certificate", "checked": "2026-11-21",
    "pages": [
      { "url": "https://www.example-plumbing.com/gas-safety/",
        "has": ["Who it's for: “Landlord gas safety certificates” in the H1", "Next step: a Book button above the fold"],
        "missing": ["No price on the page or linked from it", "No reviews from landlords"] }
    ] }
]
```

| Field | Rule |
| --- | --- |
| `name`, `wants` | The audience exactly as the owner named it, and what they come for. Never an invented persona. |
| `checked` | The date of the check, `YYYY-MM-DD`. |
| `pages[]` | Up to 5 key pages, each with its `url`. |
| `has`, `missing` | Short lines, each with evidence from the page: a quote, or where you looked. Up to 10 in each list. |

Shown as a collapsed "Audience check" panel on the Site & content tab (a section in the Markdown): each audience, then each page with "On the page:" and "Missing:". Everything is escaped, since it can quote page text. The report shows at most 4 audiences, 5 pages each and 10 items a list, and skips entries that are malformed or empty. Information only: no score, no percentages, no findings, and it never changes the score.

## The plan (setup mode only)

`/seo-setup` adds a top-level `plan`. Without it, the report is unchanged. How to fill it is in `planning.md`.

```json
"plan": {
  "status": "proposed",
  "approvedOn": "2026-11-18",
  "summary": "A marketing site with docs. Setup adds one metadata helper, a sitemap, schema and the missing /docs page.",
  "yes": [{ "id": "Y1", "what": "Redirect www to the apex domain", "why": "One host for every URL", "approved": false }],
  "pages": [
    { "url": "/pricing", "type": "Pricing page", "status": "to-build", "target": "acme pricing",
      "intent": "Someone comparing plans before signing up", "title": "Pricing | Acme", "description": "…", "h1": "Simple pricing",
      "schema": ["WebPage", "BreadcrumbList"], "parent": "/", "linksTo": ["/features"],
      "owner": { "needs": "facts", "what": "Confirm the current plan prices", "done": false }, "finding": "F-004" },
    { "pattern": "/docs/{slug}", "count": 24, "built": 0, "type": "Docs article", "status": "to-build",
      "title": "{Article title} | Acme docs", "samples": [{ "url": "/docs/install", "title": "Install Acme | Acme docs" }] }
  ]
}
```

| Field | Rule |
| --- | --- |
| `plan.status` | `proposed`: waiting for the owner. `approved`: being built. `built`: all of the agent's work is done (owner items can still be open). |
| `pages[].status` | `exists` (already right), `to-build`, `built` (done and re-checked) or `to-create` (a proposed new page). |
| `pages[].owner` | The owner's part: `needs` (`copy`, `facts`, `decision` or `yes`), `what`, `draft` (a path relative to the report, e.g. `drafts/privacy.md`, or an https address; anything else is shown as text, not as a link) and `done`. Shown as **Needs you** until `done` is true. |
| `pages[].intro` | For a new missing-parent page: its 1–2 sentence intro, built only from facts already on the site. Shown on the Plan tab; approving the plan approves these exact words. |
| `pages[].from` | The old URL when a page moves. The redirect is part of building the row, and it always needs its own yes on a live site. |
| Pattern rows | Used for sets of more than 20 pages. `pattern` + `count` (and `built`, the pages done so far). `title`, `description` and `h1` hold templates, plus up to 3 `samples` with resolved values. |
| `plan.alsoFixes` | IDs of open findings setup will also fix in code after approval. It never includes owner items, decisions or yes items. Shown on the Plan tab, so approving the plan approves these fixes. |
| `yes[]` | Site-level items that need their own yes. `approved: true` records a yes, and `declined: true` records a no. A declined item stays as a record and is never carried out. A row's `owner` can be `declined` the same way. |
| `finding` | The related finding's ID, linked from the row. |

**Progress** (computed by the renderer): each row counts once. A row that `exists` or is `built` counts 1. A pattern row in any other status counts `built ÷ count`. Anything else counts 0. Progress is the average, as a percentage.

**Default tab:** while `plan.status` is `proposed`, the report opens on the Plan tab.

## Writing well

- Plain words. "Google can't see this page's text" beats "CSR hydration issue".
- Numbers over adjectives: "38 of 40 pages" rather than "most pages".
- One problem per finding. When one helper causes three symptoms, write one finding and list the symptoms in `what`.
- `wont-fix` needs a reason in `fixed.summary` or `notes`, and the matching accepted exception goes in the SEO profile.
